# Local secrets and setup for `depgraph suggest`

Research date: 2026-11-16. This is a design recommendation, not a description of functionality already implemented. At the time of research, the PR used `OPENAI_BASE_URL`, `OPENAI_MODEL`, and an optional `OPENAI_API_KEY` environment variable. It accepts an OpenAI-compatible Chat Completions API and does not call it unless `--llm` is supplied.

## Recommendation

Keep **endpoint URL and model** in a normal named config profile; they are operational configuration, not automatically secrets. Treat internal URLs and model names as potentially sensitive metadata and do not log them unnecessarily. Put **API keys** in a secret store, never in project YAML, command arguments, Git history or a plaintext `.env`. Some OpenAI-compatible local endpoints need no key.

For interactive developer machines, offer `depgraph suggest configure` (name illustrative): ask for the endpoint URL and model, ask if authentication is required, then read a key from a hidden terminal prompt and save it to the operating system's credential store, scoped to the named profile and endpoint. Reuse it on later runs. Support status, changing a key, and deleting it without ever displaying the value. Make the model call a separate explicit `--llm` choice, with the target URL shown before names are sent; optionally let users test connectivity separately. Endpoint/model config in a user-specific config file is convenient; a repository template may contain non-sensitive settings if the organization wants, not credentials. No actual user endpoint or secret is assumed here.

Native stores: [Apple Keychain](https://developer.apple.com/documentation/security/keychain-services) (encrypted at rest and suitable for small secrets), [Windows Credential Manager](https://learn.microsoft.com/en-us/windows/win32/SecBP/handling-passwords) (CredWrite/CredRead), and the desktop [Secret Service API](https://specifications.freedesktop.org/secret-service/latest/ch03.html) on Linux. Linux access depends on a usable service and session; it can require an unlock prompt. [Secret Service locking](https://specifications.freedesktop.org/secret-service/latest/unlocking.html) explicitly allows locked collections and user prompts. Report unavailable or locked storage clearly; do not silently save plaintext. For the Rust backend, [keyring-rs](https://docs.rs/crate/keyring/latest) is one candidate; evaluate backend feature selection, maintained status, signing/access prompts, support and platform integration tests before adopting it.

For 1Password users, avoid requiring a bespoke integration initially: [1Password `op run`](https://www.1password.dev/cli/secrets-environment-variables) resolves a secret reference or 1Password Environment and injects it into the launched process. For example, a reference-only file could contain `OPENAI_API_KEY=op://Development/depgraph/api-key`, and a developer could run `op run --env-file=depgraph.env -- depgraph suggest --llm`. The vault/item names are placeholders. This requires the CLI and authorized vault access, supports centralized sharing and rotation, and avoids a plaintext `.env`; the resulting key still exists in the child environment, which other same-user processes may be able to read. References themselves can disclose metadata. [1Password's documentation](https://www.1password.dev/cli/secrets-environment-variables) explicitly warns about environment access. `op run` masking is best effort, so never intentionally print a value. [1Password release notes](https://releases.1password.com/developers/cli/).

For CI/headless, keep environment injection as an explicit compatibility option, and add an `OPENAI_API_KEY_FILE` (or equivalent file reference) so an orchestrator can mount one secret file without requiring interactive desktop storage. Specify precedence and fail if conflicting sources would otherwise hide an error; a reasonable policy is command-scoped explicit selection, then file, then environment, then configured OS store for interactive use. Document the final exact policy and keep local store unavailable failures distinct from a missing item. On headless systems, avoid prompts and do not wait for a desktop unlock. The app still reads a key into memory regardless of delivery method.

For GitLab CI, use [GitLab CI/CD protected/masked variables](https://docs.gitlab.com/ci/variables/) or an external vault; masking alone does not stop malicious job code from exfiltrating secrets. Where an external vault supports it, [GitLab OIDC ID tokens](https://docs.gitlab.com/ci/secrets/id_token_authentication/) can authenticate a job without a long-lived vault credential; [GitLab's Vault integration](https://docs.gitlab.com/ci/secrets/hashicorp_vault/) delivers the fetched value in a temporary file by default. Restrict scope and do not run untrusted merge-request code with protected secrets.

For Kubernetes, use a mounted secret from the organization's external vault where available, or a Kubernetes Secret with restricted access; keep URL/model in a ConfigMap or other non-secret configuration. Kubernetes states that [Secrets are unencrypted in etcd by default](https://kubernetes.io/docs/concepts/security/secrets-good-practices/); enable encryption at rest, least-privilege RBAC and grant access only to the needed container. Base64 is not encryption, and generated Secret manifests containing values should not be committed. [Kubernetes recommends](https://kubernetes.io/docs/concepts/security/security-checklist/) considering secret volumes rather than environment variables, since environment variables can be exposed via logs and dumps.

## Guardrails for the proposed design

- Associate a stored credential with the expected scheme, host and port, and ideally the configured profile/base path; do not silently send it when an endpoint changes. An endpoint override should not automatically forward an existing credential to an unrelated host. Disable automatic redirects for credentialed requests. Treat project-supplied endpoint configuration as untrusted: a malicious project must not be able to repoint a developer's existing key to its own endpoint. Explicit per-profile trust and key selection make that decision visible.
- Require TLS for remote endpoints; permit localhost HTTP only as an intentional local-development option. Prompt securely, do not echo or accept secrets as CLI arguments, and never include them in logs, error messages, generated config, model prompts, snapshots, test output or Git. [Microsoft's guidance](https://learn.microsoft.com/en-us/windows/win32/SecBP/handling-passwords) calls for encrypted transmission, minimal retention and no secrets in logs.
- An environment variable is a useful compatibility interface, not itself a secure vault. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) notes possible exposure through processes, logs and dumps. Prefer short-lived, scoped credentials when a provider supports them. Never promise that keychains or process-scoped injection defend against all same-user compromise.
- Test endpoint-to-credential binding and override behavior, no-key local providers, keychain locked/unavailable behavior, headless non-interaction, source precedence, key rotation/deletion, redaction, redirects, and OpenAI-compatible mock requests. Do not use a live credential in tests.
